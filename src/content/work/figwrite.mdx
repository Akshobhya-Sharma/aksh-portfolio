## Overview

FigWrite lets designers export text content from selected Figma frames
into an .xlsx file, hand it to a content team or translator, and import
their edits back to the correct text layers.

This project came out of my own personal requirement. At work, we would need to prepare content documents that were shared with the content writers, who would then re-write content where required before getting it translated from our official translation team.

<Quote>
  I was tired of manually preparing content documents and then updating Figma once verified content
  was returned to us.
</Quote>

---

## Research

This was a short phase where I spoke with `content writers`, and other designers. I needed information on how others managed content and if my solution would enable them to manage content in a more efficient way.

## Rebuilding Figwrite

<Callout tone="muted">

- Version: 2
- "Weekend" release
- May 2026

</Callout>

Once I started depending on Claude Code to add a few features I needed, I ended up rebuilding the whole tool.

<Quote>
  Phew! I did not expect a whole redesign of the architecture when I started 'weekend enhancement'
  with Claude Code as an experiment to see what the large language model (LLM) could help me with.
</Quote>

This wasn't a patch. It was a full architectural rebuild, now a
three-person effort (myself, Raj, and Dragan):

- Universally unique identifier (UUID) based identity replacing layer-name matching which survives
  renames, restructures, and file sharing.
- Two independent tabs (Export / Import) replacing one linear flow.
- Template mode to allow writing into your own existing spreadsheet format,
  not just a fresh file.
- Three import safety guards:
  - skip locked layers,
  - skip unchanged text,
  - skip blank cells,
- Dropped a content delivery network (CDN) dependency (SheetJS) for a bundled Massachusetts Institute of Technology (MIT) licensed
  library (ExcelJS) which removed a silent failure point.
- Full WCAG 2.2 accessibility pass.

## Learning from using LLMs

I was curious to see if AI can be trusted at scale. I wanted to use the project to understand the limitations of the tool and how to best use it.

After the rebuild, I ran formal review passes against the AI-written code:

- a code-quality review,
- an accessibility audit, and
- a performance/security review.

Each produced a real findings table with
severities. Each finding was either fixed, or explicitly logged as
"not fixed, by design" with a stated reason.

<Callout tone="insight" title="Examples">

- A memory-leak-prone event listener pattern, re-assigned on every
  React render with no cleanup (High severity; fixed)
- An unguarded type cast that could throw on bad input (Low severity; fixed)
- A documented decision NOT to fix postMessage('\*') because Figma's
  own plugin sandboxing makes it unexploitable. This was verified, not
  assumed.

</Callout>

## Post version 2 status

Using LLM recommended solution gave me major bugs that were detected in production.

<Callout tone="warning">

Real production bugs surfaced after release, at scale (3,000+ text nodes).

- UUID collisions from Math.random() — the collision probability
  becomes real at that volume.
- When handling large volumes, Figwrite would not export content as seen on the frame (top to bottom, left to right).
- Silent ID loss on text inside component instances — Figma's API
  throws when writing plugin data to a read-only node, and the
  original code silently swallowed that error.

</Callout>

### Fix for identified solutions

While I made some updates from v2.0.0 to v2.1.1, I need to work on the next version, i.e. 2.2.0 with the following fixes:

- switching to Figma's own native node ID instead of generating
  one with an explicit backward-compatibility path: old export files are detected
  automatically and still import correctly, with a one-time, non-error
  banner nudging the user to re-export.
- Exporting text by using Figma's `x axis` and `y axis` coordinates so that text strings export in true `top to bottom, left to right` order.

<Callout tone="muted">
  That **v2.2.0 plan** is worth naming directly as a process, not just a fix: phased, one reviewable
  chunk at a time, an explicit "do not touch" list per release, a hard build-and-lint gate after
  every phase, and decisions about what's out of scope written down as clearly as what's in scope.
</Callout>

## What I learned

The risk in AI-paired development isn't getting code that works once;
it's catching the failure modes that only show up at scale, on inputs
you didn't think to test, in places the AI didn't know to be careful (a
component instance is read-only; Math.random() collides eventually).

<Quote>
  My answer so far has been to review AI output the way you'd review any engineer's pull request
  with formal passes, severity ratings, explicit accept/reject decisions, backward compatibility
  taken seriously.
</Quote>

That process has held for two releases. What I haven't tested yet is
whether it holds on something genuinely harder. Deduplication touches
component architecture in ways the current bugs didn't, and I don't yet
know if the same review process catches problems at that level of
complexity or if scaling further means rethinking how much I lean on
AI versus doing the harder architectural calls myself.

**That's the actual open question. Not "should I use AI," but "where
exactly does my current process stop being enough."**
