## Overview

As a recreational marijuana consumer, I always felt the need to keep some record of all the cool places I have explored and all the cool marijuana strains I have consumed.

I was curious to see how many others have faced this issue and if there can be a tech-based solution for this real world issue.

<Callout tone="note">
  
- It started from a personal annoyance: sharing a joint with friends, liking it, and never
  remembering which strain it was. Same gap at retail, i.e. buy something good, no way to record it
  for next time.
- I didn't want to guess this was a real problem, so I talked to people who were
  already solving it the hard way, keeping paper diaries of what they'd tried. That confirmed the
  gap was real enough to build for.

</Callout>

3. No opportunity to see personal preference trends and other cool stats based on consumption patterns.

### Tech stack

I selected the tech stack based on it's ability to do what I needed my application to do as well as my familiarity with the toolkit.

<DataTable caption="Tech stack for Huana web-app">

| Stack                 | Purpose                                      |
| --------------------- | -------------------------------------------- |
| React, Vite, Tailwind | Familiarity and ease of design customization |
| Supabase              | For email auth only                          |
| Dexie.js / IndexedDB  | To store session data (user's input)         |
| Zustand               | State management                             |

</DataTable>

#### Why use IndexedDB?

I wanted to protect my users privacy and so, the app data had to be stored on my users browser storage.

Now, it might seem like that will increase the storage my users' browsers use and also there would be data loss if my user switched browser. This is correct and a limitation I planned for. I gave the users an ability to `export` and `import` their data so they can carry it with themselves (the output was a json file), and load it in any browser they logged into Huana with.

<Callout tone="muted">
  Privacy wasn't a tagline, it was an architectural line drawn on purpose: identity touches
  `Supabase`, consumption data never leaves the device.
</Callout>

</Section>

## Lessons with AI

AI got the basic flows working fast but layout and interaction details
were a recurring weak point.

- Buttons that weren't really designed.
- Layouts that didn't hold together until I wrote the HTML/CSS myself and described the structure in depth for it to follow.

In fact, some of the lingering UI bugs were spotted by testers who provided feedback on how the buttons didn't resize properly or the layout broke when the a text string was longer than 50 characters.

<Callout tone="insight" title="I uncovered a habbit that I should adopt when working with LLMs!">
  
  This is where I first built a habit that later carried into other projects: bringing in **a
  specialized accessibility-focused AI review pass**, rather than trusting general-purpose AI output
  on accessibility by default.
  
  This practice started here and it's the reason later projects had a
  faster, more disciplined accessibility process from day one.

</Callout>

---

## Tester feedback

I ran a feedback round with real users. None of what they found were
logic bugs, but they were interaction and polish problems that only show up
when someone uses the interface with their own hands and their own data.

- Delete confirmation dialog stayed open after the deletion had
  actually succeeded - no signal the action had worked.
- OTP paste silently failed on the first attempt (only the first
  character landed), worked fine on the second try.
- Delete button was so visually dominant it became "the main focus"
  of the card, crowding out the entry's actual content.
- A session card field used the wrong text style entirely — traced to
  one line, SessionCard.jsx:111.
- No length limits anywhere on user input (title, description,
  location) — long text broke layouts, and long pastes saved slowly
  with no loading feedback, so the app looked frozen.

## Where it stands right now

MVP was fully shipped. Every planned feature was live and deployed to Vercel. After I collected feedback from the testers, I had to take the web app offline due to temporary infrastructure I used.

A few small things are deliberately still open, left visible on purpose
rather than hidden:

- alert() calls standing in for proper toast notifications
- an unused avatarSeed field still being written to storage (dead code)
- a customProducts table defined in the schema but never used (dead code)

### What is next

**To truly build and scale Huana, I need to use more stable and permanent infrastructure on which the app can be deployed.**

I also need to resolve storage issues.

I do not have any real users yet, not because the product doesn't work, but because
there's been no marketing. That's genuinely still unresolved. I have no firm
plan yet for how to fix it, and that's an honest gap in the project
rather than a problem already solved.

---

## Learnings

Getting from idea to a working, polished build was hard, and finishing
it felt like a real win.

The harder lesson was that **AI is weakest at the thing designers care
about most: interaction and layout judgment.** You can't fully delegate
"make this feel right". I ended up writing the CSS myself and learning,
the hard way, that some problems need a specialized reviewer, not a
general one. That lesson is what made a more disciplined AI-review
process possible on every project since.
