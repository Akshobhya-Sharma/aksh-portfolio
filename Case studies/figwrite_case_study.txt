FIG-WRITE — CASE STUDY
A Figma plugin that bridges Figma text layers and Excel spreadsheets

==================================================================
WHAT IT IS
==================================================================

FigWrite lets designers export text content from selected Figma frames
into an .xlsx file, hand it to a content team or translator, and import
their edits back — applied automatically to the correct text layers.

==================================================================

workable, but brittle. Renaming a layer or restructuring a frame could

==================================================================
THE REBUILD — V2, "WEEKEND" RELEASE, MAY 2026
==================================================================

This wasn't a patch. It was a full architectural rebuild, now a
three-person effort (myself, Raj, and Dragan):

  - UUID-based identity replacing layer-name matching — survives
    renames, restructures, and file sharing
  - Two independent tabs (Export / Import) replacing one linear flow
  - Template mode — write into your own existing spreadsheet format,
    not just a fresh file
  - Three import safety guards: skip locked layers, skip unchanged
    text, skip blank cells
  - Dropped a CDN dependency (SheetJS) for a bundled MIT-licensed
    library (ExcelJS) — removed a silent failure point
  - Full WCAG 2.2 accessibility pass

==================================================================
THE PART THAT ANSWERS "CAN AI BE TRUSTED AT SCALE"
==================================================================

After the rebuild, I ran formal review passes against the AI-written
code — a code-quality review, an accessibility audit, and a
performance/security review. Each produced a real findings table with
severities. Each finding was either fixed, or explicitly logged as
"not fixed, by design" with a stated reason.

Real examples:
  - A memory-leak-prone event listener pattern, re-assigned on every
    React render with no cleanup (High severity — fixed)
  - An unguarded type cast that could throw on bad input (Low — fixed)
  - A documented decision NOT to fix postMessage('*') because Figma's
    own plugin sandboxing makes it unexploitable — verified, not
    assumed

{recommend image of: a clean visual table/grid recreating 4-5 of the
real findings above (severity, finding, fix) as a single graphic. This
is genuinely interesting to other builders and works well as a
standalone image, not just inline text. Source: build new, simple
table-style graphic, in Figma or as a styled screenshot of a markdown
table.}

Two real production bugs surfaced after release, at scale (3,000+ text
nodes):

  1. UUID collisions from Math.random() — the collision probability
     becomes real at that volume
  2. Silent ID loss on text inside component instances — Figma's API
     throws when writing plugin data to a read-only node, and the
     original code silently swallowed that error

The fix — switching to Figma's own native node ID instead of generating
one — was scoped, planned, and shipped as v2.2.0 with an explicit
backward-compatibility path: old export files are detected
automatically and still import correctly, with a one-time, non-error
banner nudging the user to re-export.

{recommend image of: a short flow diagram showing the migration logic —
"old UUID format detected -> import still succeeds -> info banner
shown -> re-export generates new format." Helps a technical reader
understand the backward-compatibility decision at a glance. Source:
build new in Figma/Figjam.}

That v2.2.0 plan is worth naming directly as a process, not just a fix:
phased, one reviewable chunk at a time, an explicit "do not touch" list
per release, a hard build-and-lint gate after every phase, and decisions
about what's out of scope written down as clearly as what's in scope.

==================================================================
WHAT I LEARNED
==================================================================

The risk in AI-paired development isn't getting code that works once —
it's catching the failure modes that only show up at scale, on inputs
you didn't think to test, in places the AI didn't know to be careful (a
component instance is read-only; Math.random() collides eventually).

My answer so far has been to review AI output the way you'd review any
engineer's pull request — formal passes, severity ratings, explicit
accept/reject decisions, backward compatibility taken seriously.

That process has held for two releases. What I haven't tested yet is
whether it holds on something genuinely harder. Deduplication touches
component architecture in ways the current bugs didn't, and I don't yet
know if the same review process catches problems at that level of
complexity — or if scaling further means rethinking how much I lean on
AI versus doing the harder architectural calls myself.

That's the actual open question. Not "should I use AI," but "where
exactly does my current process stop being enough."
